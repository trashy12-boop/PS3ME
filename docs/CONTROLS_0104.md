# Native input 01.04

Controls.cpp is SDK-independent routing/persistence code. InputRuntime.cpp feeds it pad snapshots and converts key/pen changes into actual JavaCall notifications. RuntimeServices uses this route instead of calling the fixed legacy Keypad mapper, preventing duplicate key emission. The shared pad backend still handles Start return. Begin resets routing and clears stale native queued events while the VM is stopped.

Actions are whitelisted; duplicate physical bindings aggregate into a held-key set. Buttons held while launching are suppressed until released. Neutral/disconnected pad snapshots release held keys/touch. Cursor coordinates are game LCD pixels, clamped to its bounds. Movement uses elapsed time and a bounded 50 ms catch-up, with a configurable deadzone. Drag events are limited to about 30/second. Right-stick hover only moves the native arrow; MIDP pen events are emitted on press, held movement and release.

Framebuffer keeps its last complete scaled game image separate from the cursor. The arrow is composited onto the output surface after the game image; idle cursor movement can redraw it at up to 30 fps without asking Java to repaint. Position uses the same aspect-fit rectangle as video. No cursor is written to the game's RGB565 buffer. Controls menus are native, before game launch; Start is reserved, and configuration is global rather than per game.

Tests include persistence/rejecting malformed configs, initial held-button suppression, duplicate-key release, number remapping, pen lifecycle, deadzone/clamping, polling-rate independence and output-stride/viewport guards. The native automation opens the actual settings UI, changes Cross to Key 5, saves it, then drives the actual pad-to-MIDP input path through TouchSmoke; the Java Canvas receives key 53 and pen press/drag/release. Physical pad and television output are unverified for this release. docs/CONTINUATION.md and final package test results are authoritative; earlier failures are retained for diagnosis.

Settings persistence handles CellFs rename semantics explicitly. A direct replace succeeds on POSIX; CellFs EEXIST falls back to retaining the previous valid file as controls.cfg.bak before publishing the completed temporary file. If publishing fails, the previous file is restored. Startup accepts a valid backup when the primary is absent/corrupt. A malformed primary never replaces a valid recovery file. Host tests wrap rename to reproduce EEXIST; native overwrite_fixed records the same recovery path through CellFs. This is recoverable configuration persistence, not a filesystem-wide atomic transaction guarantee.
